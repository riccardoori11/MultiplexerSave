Inside work

When you type work open atlas, a C++ process decides which workspace to open. A separate tmux server owns its windows, panes, and running programs. The server can keep them alive after the CLI exits.

How the three C++ files fit together

main.cpp makes the decisions. It asks project.cpp to turn configuration into data and process.cpp to run programs. Here is one call from start to finish.

main.cpp      open_project(paths, "atlas", …)
               └─ running("atlas")
                   └─ tmux("atlas", {"has-session"})
                       └─ tmux_args builds the argument list
process.cpp                run(args, capture, clean_tmux)
                            └─ posix_spawnp starts a tmux client
Linux                          tmux -L work-atlas has-session

The result travels back up the chain. run() waits for the child and returns a ProcessResult containing its exit code and output. running() converts exit code zero into true. That one Boolean decides whether open_project() can reuse the server.

From configuration to objects

read_project() parses the editable file into a Project. Each window section becomes a Window, and each pane command becomes a string in that window. prepare_config() passes the object to tmuxinator_yaml(), then uses write_atomic() to publish the generated files by renaming temporary files into place.

From arguments to processes

run() passes an argument vector directly to the executable. The caller chooses how output comes back. Pane queries need complete output for parsing, failures need only the last 64 KiB of diagnostics, and interactive attachment inherits the terminal. check() in main.cpp turns an unsuccessful result into an exception where success is required.

Follow an open through the code

main() calls main_impl(), which parses the arguments, resolves configuration and state directories with Paths::from_environment(), and dispatches to open_project(). If the name is omitted, current_project() checks WORK_PROJECT first, then the saved last-project file.

open_project() takes a per-project ProjectLock, reads the project, locates the plugin, and generates tmux.conf and tmuxinator.yml. It then checks the server on the project’s named socket. Expand a branch to trace what happens next.

First open · create the configured layout

With no live server or snapshot, open_project() checks that the project root exists and calls run() to start tmuxinator with the generated YAML. The YAML names the socket, root, windows, layouts, and pane commands. Tmuxinator uses these to build the workspace in tmux. The CLI checks the server is running, then calls configure_server() to set plugin options and install the detach hook. A stopped project opened with --fresh also takes this branch.

Server already running · reuse the live panes

A successful has-session check takes precedence over both the snapshot and --fresh. configure_server() reapplies settings and hooks to the existing server. The original pane processes keep running.

Server stopped, snapshot present · reconstruct the panes

saved_panes() reads the snapshot, checks its pane records and working directories, and returns the expected session, window, and pane identifiers. The CLI starts a detached tmux session, configures the server, and invokes the plugin’s restore.sh through Bash. plugin_environment() supplies the correct tmux socket context and active pane to the script.

Afterward, live_panes() queries tmux. If the identifiers match, restore_selection() selects the saved panes and windows before the client attaches. An error during configuration, restoration, or verification tears down the newly started server.

All three successful branches write last-project and release the lock. Only then does the CLI attach, unless --no-attach was requested. This ordering lets a save acquire the same lock while a client is attached.

Read open_project() and the command dispatcher

How detaching calls back into C++

tmux server     client-detached hook
                 └─ launches work save atlas --quiet
new work process    └─ main_impl() → save_project()
                         └─ run() → bash scripts/save.sh
tmux-resurrect                        └─ writes snapshot
work process        verifies snapshot against live tmux panes
  1. Register the callback. During open, configure_server() gives tmux a background shell command built by save_command(). It embeds the executable path, project name, and configuration, state, and plugin directories. Detaching starts a new invocation of the same binary.
  2. Capture the workspace. save_project() takes the project lock, checks the server, and remembers the previous snapshot contents and link target. It installs temporary plugin hooks that mark when a nonempty layout was written and when saving completed. These distinguish a successful duplicate save from a save that produced nothing.
  3. Verify the handoff. After the script exits, the CLI checks both markers and the snapshot. normalize_snapshot_directories() uses tmux’s actual pane paths to correct the saved directories. It then compares saved_panes() with live_panes(). On failure it cleans up hooks and markers and attempts to reinstate the previous snapshot before reporting the error.

Where one invocation leaves data for the next

For a project named atlas, the default config root is ~/.config/work and the default state root is ~/.local/state/work. Paths also supports XDG directories and explicit WORK_CONFIG_HOME and WORK_STATE_HOME overrides.

Config root · projects/atlas.work
init writes the editable template. Every open reads it to construct the in-memory project.
State root · projects/atlas/tmuxinator.yml and tmux.conf in the same directory
prepare_config() generates these from the project. Tmuxinator consumes the layout, and tmux reads the server configuration.
State root · projects/atlas/resurrect/last
The plugin maintains the latest snapshot here. Save verifies its pane records, and restore reads them back.
State root · projects/atlas/lock
ProjectLock takes an exclusive file lock so concurrent operations on atlas run in sequence. Other projects use their own lock files.
State root · last-project
A successful open writes the name here so the next invocation can find the project from an ordinary terminal.
